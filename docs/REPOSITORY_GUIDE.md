# DJY-OPS 저장소 생성 가이드

대자연 CU_RACING의 프로젝트를 찾기 쉽고, 다시 실행할 수 있고, 다음 팀원이 이어받을 수 있게 정리합니다.

## 1. 이름

기본 형식은 `DJY_<PROJECT_NAME>`입니다. 새 저장소는 영문 대문자·숫자·밑줄을 사용하고, 약어의 의미를 README 첫 문단에 적습니다.

| 항목 | 기준 |
| --- | --- |
| 접두어 | `DJY_`로 통일 |
| 프로젝트명 | 대상 차량·기능·목적이 드러나는 이름 또는 약어 |
| 구분 | 필요하면 `EV`, `BAJA` 등 대상을 포함 |
| 버전 | 이름의 `FINAL`, `NEW`, `V2` 대신 태그·릴리스로 관리 |
| 기존 이름 | 현재 링크와 사용 경로를 고려해 유지 |
| 예외 | 조직 프로필 저장소 `.github` 등 플랫폼 지정 이름 |

기존 예시: `DJY_EVTLMT`, `DJY_EVTQV`, `DJY_EVDTV`, `DJY_EVENGM`, `DJY_BAJA_TLMTSYS`, `DJY_ChkList`.

## 2. 언제 새 저장소를 만드는가

- 독립된 사용 목적과 실행·배포 단위를 갖는 프로젝트를 새 저장소로 만듭니다.
- 기존 기능의 수정이나 확장은 해당 저장소에서 이어갑니다.
- 함께 바뀌고 검증되는 펌웨어·서버·웹 화면은 한 저장소 안에서 폴더를 나눕니다.
- 오프라인 뷰어처럼 별도로 배포하고 재사용하는 도구는 분리할 수 있습니다. 원본 프로젝트와 동기화 방법을 문서에 연결합니다.
- 차량·하드웨어·목표가 크게 달라져 분리할 때는 이전 저장소, 분리 이유, 공통 구성요소를 기록합니다.

## 3. 처음 만들 때

1. 조직을 `DJY-OPS`로 선택하고 이름과 한 줄 설명을 작성합니다.
2. 공개 범위를 정하고 소스, 설정 예시, 문서를 추가합니다. 공개 프로젝트에는 인증정보·팀 전용 접속정보·실제 주행 DB를 포함하지 않습니다.
3. 프로젝트에 맞는 `.gitignore`와 README를 준비합니다. 외부 코드·라이브러리·자료의 출처와 라이선스를 남기고, 프로젝트 라이선스는 권리 관계에 맞게 정합니다.
4. 아래 구조에서 필요한 폴더만 사용합니다.
5. 개발 상태와 다음 작업을 기록하고, 사용 가능한 시점에 빌드·실행·검증 방법을 갱신합니다.

```text
DJY_<PROJECT_NAME>/
├─ README.md        목적·상태·빠른 시작
├─ firmware/        장치별 펌웨어가 있을 때
├─ software/        서버·앱이 있을 때
├─ web/             웹 화면이 있을 때
├─ docs/            배선·프로토콜·운용·검증 기록
├─ scripts/         빌드·실행·진단·복구 도구
├─ tests/           자동 검증이 필요한 기능의 테스트
└─ .gitignore       로컬 설정·캐시·실제 운용 데이터 제외
```

폴더명과 구조는 프로젝트 특성에 맞춥니다. 없는 구성요소를 위해 빈 폴더를 만들 필요는 없습니다.

## 4. README 기본 틀

```markdown
# DJY_<PROJECT_NAME>

프로젝트의 목적, 사용하는 대상과 해결하는 문제를 2~3문장으로 설명합니다.
약어가 있다면 의미와 관련 프로젝트 링크를 적습니다.

## 현재 상태
- 구현한 기능:
- 검증 환경과 날짜:
- 실차 적용 여부 및 적용 버전:
- 미구현·미검증 범위:

## 빠른 시작
필요한 하드웨어·도구·버전, 설치, 설정, 실행 순서를 적습니다.
실행 성공을 확인하는 방법과 상세 문서 링크를 포함합니다.

## 구성
주요 폴더와 데이터 흐름을 설명합니다.
장치가 있으면 배선·핀맵·통신 정의 문서로 연결합니다.

## 검증
실행할 검사, 시험 조건, 예상 결과와 실제 확인 범위를 적습니다.
빌드 성공·벤치 시험·실차 시험을 구분합니다.

## 다음 작업
- 다음으로 검증하거나 구현할 항목

## 참고 자료와 라이선스
외부 소스·문서·라이브러리의 출처와 적용 라이선스를 적습니다.
```

## 5. 개발 기록과 인수인계

- **변경 이유:** 무엇을 왜 바꿨는지 커밋·PR·문서에 남깁니다.
- **적용 버전:** 실차 적용 시 소스 커밋, 빌드 설정, 하드웨어, 보정값, 적용 날짜를 연결합니다. 예를 들어 검증한 릴리스에 `v0.1.0` 태그를 사용합니다.
- **검증 범위:** 빌드 성공, 합성 데이터 시험, 벤치 확인, 실차 확인을 각각 표시합니다.
- **측정 의미:** 신호 출처·단위·시각 기준을 기록하고 실측값과 계산값을 구분합니다.
- **이전 자료:** 보존 자료에는 당시 버전과 대체된 문서 링크를 남겨 현재 운용 절차와 구분합니다.
- **다음 작업:** 진행 중인 문제와 재현 방법, 필요한 장비, 확인해야 할 항목을 남깁니다.
